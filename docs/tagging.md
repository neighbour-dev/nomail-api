# Git Tag 规范

## 1. 命名格式

版本标签统一使用小写 `v` 前缀，遵循语义化版本：

```text
稳定版：v<MAJOR>.<MINOR>.<PATCH>
测试版：v<MAJOR>.<MINOR>.<PATCH>-beta.<序号>
```

| 类型 | 示例 | 用途 |
|---|---|---|
| 稳定版 | `v0.1.0` | 正式发布 |
| 测试版 | `v0.2.0-beta.1` | 需要用户参与验证时使用 |

- 主、次、修订版本号为非负整数，不允许前导零。
- 测试版只使用小写 `beta`，序号从 `1` 开始。不区分 alpha、rc 等阶段。
- 可以直接发布稳定版，不要求先发布测试版。
- 不使用 `latest`、`release-1.0`、`V1.0.0`、`v1.0` 等作为版本标签。
- 不使用 `+build` 构建元数据，例如 `v1.0.0+20261101`。

## 2. 版本递增规则

- **MAJOR**：不兼容变更，例如破坏现有 API、配置或数据兼容性。
- **MINOR**：向后兼容的新功能。
- **PATCH**：向后兼容的问题修复。
- `0.x` 开发阶段，破坏性变更提升 MINOR；PATCH 仍只用于兼容修复。
- 同一目标版本的测试版序号递增；转为稳定版时去掉 `-beta.<序号>` 后缀。

示例：`v0.2.0-beta.1 → v0.2.0-beta.2 → v0.2.0`；不需要测试版时直接发布 `v0.2.0`。

## 3. 创建与推送

- 标签名必须为 `v` 加上该提交的项目版本，例如项目版本 `0.1.0` 对应 `v0.1.0`。
- 使用 **annotated tag（附注标签）**；具备签名条件时也可使用 `git tag -s`。
- 确认目标提交后创建标签，只推送本次标签，不使用 `git push --tags`。

```bash
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin v0.1.0
```

推送版本标签会触发镜像和 GitHub Release 自动发布，发布前的准备见[贡献指南](../CONTRIBUTING.md#version-maintenance)。

## 4. 不可变原则

- 已推送的版本标签不得删除、移动或强制覆盖。
- 同一个版本号只对应一个提交，不复用已发布的版本号。
- 需要修改代码时，递增版本并创建新标签；预发布使用下一个序号。
